# Private matching calibration intake

`/calibration` is a local owner workflow. It records matching judgments and a separate matching qualification approval. It grants no source request, duplicate decision, candidate fact, packet approval, disclosure or application permission. Retained-corpus comparison evidence does not refresh a source observation or make a role eligible for preparation.

## Owner workflow

1. Open the page through the normal local session. The active stored profile must match the actual private profile file; a demonstration profile is never substituted.
2. Select genuinely distinct retained jobs and preview their duties and original provider, tenant, posting, job-version and observation identities. Preliminary availability hints disable records with a missing provider payload, unsupported provider, missing qualified completed-run lineage or unsupported owner-correction replay. A selectable hint proves only those necessary conditions; the exact selected preview still validates the full parser, content and subject bindings. Direct duplicate suggestions remain visible and selectable. A known direct owner-linked pair cannot count as two jobs; no global duplicate-clearance requirement is added.
3. Choose a new threshold version, label-agreement minimum, **positive** pair minimum and pair-agreement minimum. All controls start blank. Basis points range from 0 to 10000. Precommit freezes those choices and the selected final-version corpus before outcomes are displayed. A threshold version is unique and cannot be edited or reused for a different campaign.
4. Review the actual duties and VERIFIED candidate context, then provide each match label and occupation family. Families describe duties, not employers, seniority or remote/part-time arrangements. `UNKNOWN` is retained as incomplete and does not count toward the four-family requirement. Labels are not derived from scores. Revisions append history and the latest genuine event counts once.
5. Select two campaign jobs in the read-only pair preview, review both contexts and choose a preference. Neither side is preselected. Reversing the same pair is a revision, not another pair. A score tie remains disagreement; the software never chooses a preference.
6. Review the assessment. The unchanged assessor requires at least 30 complete unique labels, four actual occupational families, all three derived eligibility statuses, the precommitted performance thresholds and pair sample, and all eight executable safety proofs. It remains uncalibrated or pending until the real evidence satisfies those requirements. Then the separate **Approve this matching qualification** button binds the exact assessment. Technical AI review cannot supply this approval.

If a form expires or its context changes, the page shows current durable state. It never retries, retains a choice as a new confirmation, or infers a successful write from a browser acknowledgement. Session, same-origin, exact subject/context and one-use nonce checks run on the server. Old open forms become stale after any campaign judgment changes; review the refreshed page before another deliberate choice.

## Comparison and qualification evidence

The additive schema15 migration creates five empty tables: campaigns, comparisons, label events, pair events and intake qualifications. Historical labels, pairs, jobs, normalizations, evaluations and source history are retained. Engineering rollout does not create an owner campaign, comparison, label, preference, threshold choice or approval.

`CALIBRATION_OFFLINE` comparisons are rebuilt by the production pure source reader, final normalizer, eligibility engine and scorer from immutable retained payloads and the active verified profile. Each snapshot binds the original identity and content/raw-payload hashes, qualified source lineage, exact job/profile versions, final engine tuple and outcomes. Historical parser derivation bindings retain their original versions; they are not relabelled as current results. The new comparison does not overwrite the canonical job or evaluation. Scorer/weight/golden versions remain separately bound.

Every judgment records the actual server-consumed local-owner gate and exact displayed subject, prior revision and current context. The selected values and provenance are included in immutable event digests. Both event kinds form one append-only context chain; database triggers reject updates and deletion. Nonce/session values are never persisted. These are consistency and local-owner provenance checks, not a digital signature or independent proof of the owner's identity.

The technical collector (`npm.cmd run r2:calibration-safety`) retains individually named actual test/audit results for executable golden corpus, determinism, monotonicity, ablation, bounds, recommendation invariants, privacy audit and migration integrity. The server validates the current clean Git head/tree, engine tuple, test-source blobs, exact required passed cases without skips, artifact/log digests and immutable migration manifest. It reads the fixed private runtime record; forms cannot post boolean gates or a substitute bundle. Missing or stale evidence stays pending. The pure DB layer receives this already validated context from the trusted server; it performs no hidden filesystem or Git access.

Qualification writes the actual existing calibration run and its new intake link in one SQLite transaction, including safe audit records. Failure rolls back all of them. The shared currentness validator reconstructs the campaign, comparisons, latest event chain, thresholds, actual safety evidence and exact separate approval, and reruns the unchanged assessor. Source/job/profile/engine/corpus/evidence/event drift prevents reuse. Historical unbound aggregate runs remain readable but cannot qualify a new current release. New `CALIBRATED` evaluation admission and the official private-readiness criterion use this validator; uncalibrated evaluation remains supported.

## Privacy and recovery

Retained source text is rendered as escaped text, with no remote images, executable HTML or automatic provider navigation. The page exposes relevant VERIFIED profile context and explicit unknowns, excluding raw profile files, identity/contact details, cookies and tokens. Errors render only closed safe codes. Private snapshots, judgments, backups and safety artifacts stay local and ignored by Git.

Preserve the append-only history if a campaign becomes stale. Start a new campaign only through an actual owner threshold/corpus choice; never rewrite old snapshots, manufacture statuses/families, tune thresholds automatically, or backfill approval. A reviewed code revert can disable intake while preserving schema/history. A restore must follow the existing current-event reconciliation and backup procedure; it never authorizes replay of an external action.
