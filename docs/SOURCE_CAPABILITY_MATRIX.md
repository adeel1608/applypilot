# Source capability and policy review

Reviewed 2026-09-08 using official vendor documentation only. No real listing, search endpoint, authenticated account, or application URL was fetched for this review. Documentation access is not live discovery. The implementation has bounded Greenhouse and Lever GET readers but **zero enabled production capabilities**. The exact R1 design is in [R1 source-enabled Beta plan](R1_SOURCE_ENABLED_BETA_PLAN.md).

## Beta Core implementation state — 2026-09-08

Greenhouse list/detail and Lever paged list/detail are implemented behind one ignored `data/private/source-allowlist.json` boundary. Configuration binds source, tenant, operation, exact HTTPS host/path, approval/policy version, expiry, and request/record budgets. DNS/address/redirect, credential URL, timeout, size, loop, 401/403/429, and capability checks fail closed in fictional injected-transport tests. Discovery runs and observations have durable safe metadata. No private allowlist is present and no real tenant call is authorised or made, so the owner-facing release state remains `WAITING_FOR_APPROVED_TENANT` (the current internal compatibility code is `SOURCE_READY_AWAITING_TENANT`).

Before activation, R1A must close the remaining production boundary: separate policy and capability expiries/approval reference, page/byte/time/redirect/retry caps in the persisted contract, connection-time DNS pinning to remove the pre-resolution/fetch rebinding gap, a deadline that covers full body consumption, typed audit allowlists, and revocation checks before every request. Existing reader code is a strong fail-closed foundation, not authority to call a tenant.

Each source needs an owner-approved capability record: source + tenant + operation + documented interface + terms/robots review date + allowed hosts + budgets + expiry + approval reference. An API being public does not by itself authorise this use. No account/tenant enumeration, hidden-endpoint reverse engineering, or security bypass. Missing permission or unclear evidence means disabled.

## Terms, robots, and access gates

SEEK's current terms require prior written consent for automated extraction and constrain copying/aggregation. Its limited personal-use provision does not enable an automated adapter. Preserve the existing supplied-content-only gate. [SEEK terms, sections 7, 9 and 10](https://au.seek.com/terms).

Indeed restricts bots, scraping and automated submissions without express permission, subject to its stated exceptions. The existence of a publisher plugin or permitted AI connector does not show ApplyPilot is approved. Partner integrations are limited to their approved purpose. [Developer agreement](https://docs.indeed.com/legal-terms/developer-agreement), [Indeed terms](https://www.indeed.com/legal?hl=en).

LinkedIn prohibits unauthorised scraping and automation. Keep discovery manual, even when a page is publicly readable. [LinkedIn User Agreement](https://www.linkedin.com/legal/user-agreement).

For Greenhouse, Lever, Workday, Employment Hero and each generic employer, record interface terms and employer-specific restrictions before activation. This research did not examine individual employer robots files: no employer/source has been newly enabled. A permissive robots file does not grant authorisation; robots is not an access-control mechanism. [Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309.html).

## Recommended forward order — proposal, not activation

1. Lever public Postings GET for one owner-chosen, policy-approved site/region: first smoke is one list page, at most 25 records, no redirect/retry/detail.
2. Greenhouse public Job Board GET for a small owner-chosen, policy-approved board after validating that its all-posts list fits the local response/record cap.
3. Selected generic employers with clearly documented public feeds and permissive use; no generic web crawler.
4. Employment Hero only with legitimate organisation/API permission; Workday only after a documented tenant-specific read path is approved. Their order depends on real access, not old phase numbers.
5. Indeed and SEEK only if an explicitly permitted integration supports the intended candidate use. LinkedIn remains manual unless a new approved technical/policy review establishes a legitimate alternative.

This reorders old Phase 5 ahead of Phases 3/4. Australian job coverage must be measured against the owner's privately maintained employer allowlist; no claim that these ATSs cover most Australian casual vacancies is made. Local paste remains the broad low-cost intake path where the owner may legitimately supply content.

## R1 implementation contract and acceptance

The exact capability fields, DNS-pinning/body-timeout design, retry/cancellation/crash rules, tenant isolation, approval workflow, and one-tenant smoke are normative in [R1 source-enabled Beta plan](R1_SOURCE_ENABLED_BETA_PLAN.md). This matrix supplies the current evidence and source ordering; it does not activate either reader.

- Candidate-blind connector: approved source/tenant query -> bounded HTTPS GET -> Zod source record -> inert description -> identity/provenance -> review/canonical job. Never send profile, answers, documents, cookies or candidate preferences containing private prose.
- Scope exact HTTPS host/path; validate resolved addresses and every redirect; deny loopback/private/link-local/metadata addresses, credentials, non-HTTPS, unapproved redirects, and mixed encodings. Do not reuse the current display-only URL classifier as an SSRF guard.
- Proposed default ceiling: one in-flight request per tenant, at most 30 requests and 500 records per owner-started run, explicit page/byte/time caps. These are internal safety limits, **not** source-approved quotas. Lower limits prevail; 429 or restrictions pause and require the documented recovery policy, never proxy rotation.
- Persist run ID, source record ID, tenant, parser/policy versions, timestamps, cursor, bounded error codes, and immutable raw snapshots locally. Same-page repeats and cursor loops must terminate. Changes do not erase old provenance.
- Fixtures cover pagination endings, repeated cursors, malformed/oversized HTML/JSON, expiry, 401/403/429, redirects/DNS rebinding, duplicate/requisition conflicts and interrupted reruns. Acceptance requires zero private outbound payloads, no write methods, bounded retries, idempotency, and human review of a narrowly authorised read-only smoke run.
- Rollback: disable the individual capability without deleting existing jobs or source records. No future reader obtains application-write authority.
